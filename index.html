Your software, as an ontology.

Instead of a pile of pages, a living model of the real things in your system, how they connect, and what can be done when one changes.

Objects

The things your team works with, each with its own properties.

  • Service
  • API
  • Doc page
  • Runbook
  • Decision
  • Ticket
  • Owner

Links

How those things relate, so a change in one shows what else it touches.

  • exposes
  • documented by
  • decided in
  • changed by
  • owned by

Actions

What the brain and your team can do, always with a person approving.

  • Flag as stale
  • Draft update
  • Request review
  • Publish

How it works

From "something changed" to "the docs are right again", with a person approving every edit.

  1. Bring it in

    Drop in PDFs and files, or connect GitHub, Jira and Confluence. Everything becomes plain markdown.

  2. Build the ontology

    Services, APIs, decisions and pages become objects, linked to the code and tickets behind them.

  3. Spot what's stale

    When a pull request or ticket touches something, every linked page is checked and flagged if it no longer matches.

  4. Approve the fix

    You get a drafted update with its sources. Accept, edit or reject it. Nothing publishes without you.

Built on files you own.

Your knowledge lives as markdown in your own repository, not locked inside another tool.

  • Plain markdown in git. Read it, diff it and review it like code.
  • Every page shows its sources. Linked PRs, tickets and documents sit in the file.
  • Leave any time. Your files keep working without us.
